Backlog do Produto de Software

O Backlog do Produto foi elaborado com o objetivo de organizar e priorizar os requisitos necessários para o desenvolvimento do sistema de monitoramento e navegação autônoma do Micromouse. Sua estrutura é baseada em histórias de usuário, requisitos não funcionais e critérios de aceitação, permitindo a rastreabilidade das funcionalidades ao longo do ciclo de desenvolvimento.

As funcionalidades foram agrupadas em épicos que representam os principais domínios do sistema, abrangendo desde a navegação autônoma do robô e a comunicação de telemetria até a interface web e o histórico de corridas.

Cada história de usuário foi escrita seguindo o padrão “Como [ator], quero [funcionalidade], para [benefício]” e classificada conforme a técnica de priorização MoSCoW (Must Have, Should Have, Could Have e Won't Have), auxiliando na definição do escopo de cada entrega.

Além dos requisitos funcionais, o backlog contempla requisitos não funcionais relacionados à autonomia do robô, desempenho da telemetria, persistência dos dados e escalabilidade da solução. Os critérios de aceitação e as tarefas associadas a cada item servem como referência para implementação, validação e acompanhamento das atividades do projeto.

Épico B: Navegação Autônoma

ID Título da História MoSCoW História de Usuário Critérios de Aceite
US-05 Explorar o Labirinto Must Have Como avaliador, quero que o robô explore células desconhecidas para construir um mapa do ambiente. CA-05-01: Dado que existam células desconhecidas, quando o robô explorar o ambiente, então deverá priorizar sua visita.

CA-05-02: Dado que uma nova célula seja visitada, quando a exploração ocorrer, então o mapa deverá ser atualizado.

CA-05-03: Dado que a exploração esteja em andamento, quando uma célula já conhecida for encontrada, então o sistema deverá manter a consistência do mapa.
US-06 Detectar Obstáculos Must Have Como avaliador, quero que o robô identifique obstáculos para evitar colisões. CA-06-01: Dado que exista um obstáculo à frente, quando os sensores realizarem a leitura, então o avanço deverá ser bloqueado.

CA-06-02: Dado que exista uma parede lateral, quando ela for detectada, então deverá ser registrada no mapa.

CA-06-03: Dado que o sistema calcule possíveis movimentos, quando houver uma célula bloqueada, então ela não deverá ser considerada navegável.
US-07 Atualizar Mapa Must Have Como avaliador, quero que o mapa seja atualizado conforme novas informações são descobertas. CA-07-01: Dado que novas informações sejam descobertas, quando forem processadas, então o mapa deverá ser atualizado.

CA-07-02: Dado que uma parede seja identificada, quando a célula for atualizada, então a informação deverá ser persistida.

CA-07-03: Dado que o mapa seja transmitido ao sistema web, quando solicitado, então deverá refletir o estado atual conhecido.
US-08 Encontrar Objetivo Must Have Como avaliador, quero que o robô encontre a região objetivo do labirinto. CA-08-01: Dado que o robô alcance a região objetivo, quando sua posição for analisada, então o objetivo deverá ser considerado encontrado.

CA-08-02: Dado que o objetivo seja encontrado, quando a exploração estiver ativa, então a corrida deverá ser marcada como concluída.

CA-08-03: Dado que a conclusão seja detectada, quando a telemetria for enviada, então o status deverá ser atualizado.
US-09 Planejar Rota Must Have Como avaliador, quero que o robô calcule rotas eficientes para alcançar o objetivo. CA-09-01: Dado que exista um mapa conhecido, quando o algoritmo calcular uma rota, então deverá retornar um caminho válido.

CA-09-02: Dado que existam múltiplas rotas possíveis, quando forem comparadas, então deverá ser escolhida a mais eficiente.

CA-09-03: Dado que uma rota seja gerada, quando o robô iniciar o deslocamento, então deverá conseguir percorrê-la.

CA-09-04: Dado que haja um obstáculo, quando os sensores o detectarem, então deverá replanejar a rota.

Tabela de Requisitos Não Funcionais (RNF)

ID HU REQ Pertence ao USM Descrição Critérios de Aceitação Tarefas
RNF-SW-001 O painel web não deve enviar comandos ao Micromouse durante a corrida. Todas as releases > Autonomia Garante que a decisão do robô permanece embarcada e independente. Revisão da interface não encontra botões/endpoints de comando; testes confirmam que mensagens do frontend não alteram rota, velocidade ou estado de decisão. Revisar rotas; revisar WebSocket; criar teste negativo; documentar restrição.
RNF-SW-002 A telemetria não deve bloquear a rotina de navegação do Micromouse. Release 2 > EP-SW-05 O envio de dados deve ocorrer em paralelo ou com tolerância a falha de rede. Em simulação, se o servidor estiver indisponível, o algoritmo continua decidindo rotas; falha de envio gera registro de erro sem parar navegação. Definir fila/buffer; tratar falha de rede; criar teste de servidor indisponível.
RNF-SW-003 O software deve aceitar labirinto 4x4 e ter modelagem preparada para 8x8 e 16x16. Release 1 > EP-SW-02 O tema oficial cita três tamanhos. Criar labirintos 4x4, 8x8 e 16x16 no modelo sem alterar o schema. Validar tamanho; testar criação; alinhar escopo visual com a equipe.
RNF-SW-004 Os dados armazenados devem ser consultáveis após encerramento da aplicação. Release 1 > EP-SW-02 O SQLite deve manter resultados entre execuções. Após reiniciar o backend, corridas previamente salvas continuam sendo retornadas pela API. Testar persistência; configurar arquivo SQLite; documentar local do banco.
